# 按问题选择上下文与分段回复

2026-10-27回复语气：模型结合当前问题与背景判断专业性和交流情境。专业问题准确清楚、减少公文腔；日常问题使用自然口语，可适度风趣、接梗或使用贴切比喻，不强制每条搞笑。严肃或情绪低落情境认真体贴，混合问题优先准确有用，遵循对方明确的语气偏好；不对外输出分类标签。执行进度同样减少客服套话，事实与来源要求保持。

2026-10-26对外措辞：固定读取进度改为“我先读取你引用的内容，再根据实际内容分析。”，引用引导、处理失败等固定回复也使用“内容”。模型提示词要求优先称“引用的内容”，类型明确时自然称图片、链接、视频或消息，app_message、卡片和文本不统称附件；内部attachment字段及授权逻辑保持。93项回归通过。

业务层保存的完整消息记录，不等于每次都发送给模型。`adaptive_context=true` 默认启用以下流程：

1. 群聊与私聊采用相同规则：无原生引用时提供同会话最近最多12条消息；有原生引用时提供引用目标本身及其前后各最多12条消息，合计最多25条，按采集顺序排列。不用“刚才、继续”等关键词决定是否提供历史。
2. 模型认为仍不够，可指定 recent/reference/search、条数和精确搜索词补充。context_limit在reference模式表示每侧条数，其他模式表示总条数，均最多12。背景封套不超过16 KiB，内容过长时可能少于条数上限；引用模式优先保留目标和附近消息，不用另一侧补齐不足的一侧。只选触发事件之前已采集的消息，当前请求独立提供，后到消息不改变正在执行的目标。引用目标未在本地记录中找到时返回空背景及原因，不猜测位置；精确引用仍由MCP单独解析。背景不足时询问或按范围补查，不自动改成全量历史。模型输出 context_mode=none 仅表示无需追加背景，不表示本轮没有使用历史。
3. 默认窗口只是候选背景。模型自行判断相关性，可使用部分、全部或完全忽略；无关时直接回答，不强行关联历史。需要更多背景时主动请求recent/reference/search，可用search查询默认窗口之外的相关历史。每次查询仍有条数、字节和候选扫描范围限制，同一范围重复请求不会自动翻页。context_mode=none不强制使用背景，也不从同题SDK线程中物理删除此前已经提供的内容。按账号、会话和参与者区分归属。群聊保留其他参与者的问答背景，交由模型结合 sender_id、reference 和当前请求判断关联；它们不自动成为当前用户的指令或附件授权。人工出站可作背景；自动回复通过可信排序序号排除原生回显，已落盘的回答作为 assistant_reply 引入一次。明确引用机器人原生回复时保留该目标，避免把引用目标也当重复回显过滤。附件只提供元数据及既有结果，不因选择上下文而重新读取原附件。
4. 每个新问题建立独立 SDK 执行线程，旧会话线程映射保持。避免旧线程隐含把此前所有文字和图片自动带入；同一问题各段共享其执行线程，重启继续使用已保存 task_thread_id。完整业务原文及派生内容仍按7天保留，既有 Codex 线程不删除。

2026-10-26按用户澄清改为执行决定即时输出：无需用户明确要求分阶段。模型主动用对外commentary说明下一执行决定，监听器从同一turn的流式事件即时发送；缺少commentary时，根据真实工具开始事件发送简短操作说明。仅转发对外进度，禁止转发reasoning、原始命令参数、凭据、工具输出或最终schema JSON。工具执行、进度和最终答案在同一轮内连续进行，不为发送“正在处理”而另起模型轮次。

模型计时分为以下阶段，配置保存在agent状态目录的`config.json`，旧配置缺少新字段时使用默认值：

- `startup_timeout=60`：独立限制SDK状态检查、轮次启动和运行时准备。收到本轮`wechat_message`输入完成事件后，才开始响应预算；旧运行时缺少该事件时，本轮首个模型消息、reasoning或工具事件也可标记准备完成。只有reasoning的后续活动不会续期。无流式接口的兼容实现从启动调用返回后开始响应预算。
- `decision_timeout=30`：准备完成后等待下一执行决定、正文增量或最终答复的预算。已开始的SDK工具调用独立使用`tool_timeout=180`；工具完成后重新开始决定预算。多个并行工具分别受各自上限约束。
- `generation_idle_timeout=30`：本轮收到非空`item/agentMessage/delta`后，按最后一次正文增量计算停滞时间。同一消息的后续增量可以续期；空增量、reasoning和无关turn事件不能续期。增量仅用于内部计时，不转发未完成正文或schema JSON；最终回复仍经完整解析、校验及原有幂等发送流程。
- `turn_timeout=600`：从SDK状态检查开始计算的单轮总时限，覆盖启动、响应、正文、工具及进度发送，正文持续产生也不能突破此上限。分段续写的各SDK轮次分别计时。

以上值均允许0.05至600秒。进度发送仍有15秒观察上限；资源下载/附件预处理保持各自限制。超时后中断准确轮次并观察结束状态；启动调用超时且未获得轮次ID时保留未知状态、暂停会话，不自动启动第二次请求。中断确认及微信发送另需时间，这些预算不是对端收件时限。

`continue_reply`、`next_step`及上下文范围字段保留，供最终长答案续写或按需背景补充使用，不再用它们代替即时执行进度。每个问题进度及最终回复合计最多64段，索引0至63，保留最后一段结束；达到进度上限停止模型并说明，不静默越界。每段先落盘，通过MCP `reply_text_part`提交；MCP重新校验原触发事件账号、会话和群真实@，先创建该段唯一意图，再调用原生文字发送。只有上一段accepted且未结束才能继续。进度发送响应丢失只查原段，状态未知则中止当前模型并暂停会话，禁止跳段、换ID重发或改写原段。旧`reply_text`单条意图保持兼容，同一事件不能混用。

业务状态 `continuing` 表示上一段已接受、下一段还未生成；可在重启后继续。`generating` 中断仍需核查，不自动重跑；`sending` 重启后只查询原段。每段都有独立服务器消息ID/发送回显精确关联。旧消费进度、thread映射及发送去重记录不会重置。

流式进度在`generating`状态下记录`progress_pending`及`progress_key`；接受后追加到parts并推进同一part_index。若此时崩溃，按generation_unknown暂停，不把进度误当最终草稿重发，不自动重跑活跃工具。[官方App Server事件说明](https://learn.chatgpt.com/docs/app-server)；本机固定SDK 0.163.0使用turn.stream()和其原有结果收集器，避免消费全局通知串入其他会话。

进度文案只与同一次完整回复流程中上一条已accepted消息比较（去除首尾空白）：A→A跳过第二条，A→B→A三条都发送。上一条从持久化parts恢复，安全续接也保持该规则。SDK同一事件key仍按身份幂等，不能因中间发送过其他内容而重放旧事件。跳过的文案不占段索引，工具照常继续，不同进度与最终答案正常发送。新请求独立计算，不跨请求/跨会话去重；发送未知的原段仍暂停，不能用文案去重掩盖未知结果。
