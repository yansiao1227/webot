# 4.1.9.30 朋友圈原生实现

## 当前发布边界

原生公开文字发布存在未核实完整的上下文差异：正常 UI 按返回值非空条件附入 `micromsg.WCExtInfo`，侧车省略该字段；ClientId 来源也未证明等价。已有发帖完成后延迟安全退出样本，尚未获得具体风控原因码，不能把任一差异直接当作根因。

公开文字发布入口提供原有原生实现，能力按已构建侧车及 ABI 检查报告。固定版本、模块摘要、进程实例、账号和参数校验仍执行；旧意图与诊断保留，查询不重放。没有无条件禁用发帖的代码或启用开关，调用频率、额度、账号异常暂停与人工恢复仍由 MCP 执行。

入口开放不代表安全退出问题已经解决。真实 UI 参数与上下文、退出原因仍需核实；不能以伪造扩展、盲改 ClientId、增加随机延时或清除账号标志声称问题已解决。下文原生成功返回与分层调整内容为历史证据，不是长期安全性证明。

本节只依据代码、已有反编译及本地验证记录。未访问微信进程、未发送网络写请求、未重新登录或解除停写。
没有微信侧风控原因码、完整请求报文或正常 UI 同条件对照，不能确定唯一触发原因。

### 原生调用方式

- 工作确实投递到与原 SNS 包装相同的 `1f930 -> 20f20 -> 291280(flag=1)` 队列，已记录同一回调线程；
  不能据此推断完整 UI 业务流程已复现。
- 点赞、评论及发布直接调用网络包装，省略了 UI 模型构造、部分状态更新和通知链。这是确定的调用差异，
  是否影响平台检测未知。
- 每次 RPC（包括查询）均创建远程线程；首次加载还通过远程线程加载侧车。
  验证期间使用三个侧车版本。未安装新跳转 Hook，但仍存在 DLL 加载及远程执行行为，不能等同普通 UI 操作。
- 早期等待循环设置为约 100–250ms；一次 `mode=1` 查询不是一次新的业务写请求，
  但仍会访问进程并创建查询线程。没有完整历史 RPC 次数日志，不能把业务 `calls=1` 当作查询线程数。
  当前生产等待循环已降低频率，但不能据此宣称规避检测。

### 请求参数差异

| 字段／过程 | 原客户端路径的静态证据 | 当前构造 | 判断 |
| --- | --- | --- | --- |
| Action.Source `+0x2c` | `2c14560` 从联系对象 `+0x244` 读取 | 固定 `0` | 已确认差异；没有证据证明 0 对所有目标都等价 |
| Action.CreateTime | `2c14560` 使用 root 虚表 `+0x48` 的返回值 | Windows FILETIME 转 UTC 秒 | 取值路径不同；getter 的时间校正／语义尚未完全核实 |
| ClientId | 正常路径有自己的生成逻辑；发布取模型中的 ClientId | 使用稳定的自定义请求 ID／哈希 ID | 有利于本地幂等，但格式与原生生成过程未证明等价 |
| 发布 XML 与默认位图 | 原模型 serializer 和发布构造 | 复现公开文字的最小字段及默认值 | 有结构证据和成功返回，缺少同条件正常 UI 请求的逐字段对照 |
| 点赞／取消／评论枚举 | 好友点赞 Action.Type=1，评论=2，取消为另一消息的 ObjectOp=5 | 分别使用 1、2、5 | 未发现把取消点赞枚举误用于普通点赞的证据；非好友分支拒绝执行 |
| 网络 options | 首个 int 为重试计数，默认值 `0x1d4c000000000` | 低 32 位为 0，高 32 位为 120000 | 未发现应用额外启用原生自动重试；不代表底层网络完全没有重传 |

请求参数与调用链不完全等价是需要继续离线核实的高优先级问题，不能以返回两个零状态就排除。
返回成功表示该次业务处理结果，不表示账号健康、后续策略检查或内容最终可见性已确认。

### 分层调整后的处置

上述复盘保留为历史证据。用户已明确结束人工停写并将业务策略移交 MCP：Hook 不再读取旧开关、限流或暂停记录，但继续保留原请求防重与未知状态不重放。此次仅做本地回归，没有重新做真实写测试。后续策略、验证边界及未完成事项见[MCP handoff](../../wechat_mcp/docs/SNS_HANDOFF.md)。

## 构建与运行边界

在项目根目录先构建通常的运行时，再构建独立侧车：

```powershell
.\client_hook\scripts\build_runtime.ps1
python -B -X utf8 .\client_hook\scripts\build_sns_sidecar.py
```

构建不会加载 DLL 或执行微信操作。产物位于新的 `build/sns-*/`，由 `sns-current.json` 指向，
不覆盖任何已加载文件。侧车首次调用时核验核心 SHA-256、进程实例、账号和固定入口字节后加载并保持驻留；
它不安装新的跳转 Hook，不动态卸载。请求绑定当次构建，查询不得加载新侧车或创建新意图。
HTTP、SDK 与状态字段见 [API.md](API.md)，MCP 策略接入见[交接文档](../../wechat_mcp/docs/SNS_HANDOFF.md)。

`sns_sidecar.c` 复用与 SNS 原生包装一致的 `1f930 -> 20f20 -> 291280(flag=1)` 队列，
先用无副作用 probe 核对回调线程与引用释放，再在该队列调用网络包装。远程线程只登记、入队及查询。
源 protobuf 的嵌套字符串和消息使用借用对象，网络包装深拷贝后才继续执行；借用源不交给原生析构。
结果中的原生字符串及共享引用按客户端分配器单独清理。非零错误、超时、异常或清理未确认均保持 `unknown`，不重发。

未完成请求不会因为重新登录、构建或重启自动重放。旧 Hook 业务暂停记录不参与执行判断；MCP 的授权、暂停及旧未知意图的人工结案另见交接文档。

## 可复现的离线分析

在项目根目录执行，`<DLL>` 为上述构建的 `Weixin.dll`。工具不读取账号数据库、不附加进程、不发送网络请求。

```powershell
python -B -X utf8 .\client_hook\analysis\analyze_sns.py --artifact <DLL>
```

`RE_WECHAT_OBJDUMP` 使用根目录 `.env` 配置；也可用 `--objdump <程序路径>` 指定。
默认输出为 `client_hook/build/sns-analysis/`：

- `sns-analysis.json`：哈希、字符串位置、RIP 引用、指令对齐结果和证据限制。
- `<RVA>.asm`：从 `.pdata` 函数起点解码的汇编。
- `ranges.txt`：供 `analysis/ExportSelected.java` 使用的绝对 VA 范围。

支持 `--seed <完整字符串>`（可重复，替换默认种子）、`--radius 0`（仅精确目标）和 `--output <目录>`。
使用 `--table <RVA>` 读取显式指定候选表的前六个指针槽，可重复指定；输出保存原始 VA、
可执行节归属与精确 unwind 入口。表可能短于六槽，因此不能把相邻数据当作虚函数，工具不推断槽语义。
使用 `--entry 0x1cbdde0` 同时追踪候选函数的直接 CALL/JMP 与 RIP 函数指针引用；
可继续用 `--entry 0x8604c0 --entry 0x85e550` 追踪关联信号的发射方。
默认半径 64 字节用于寻找相邻数据结构，`target_delta != 0` 的命中**不是**字符串交叉引用。
工具只覆盖部分 RIP 相对指令，负搜索不能证明不存在实现。

使用已有 Ghidra 项目时，需把以下参数传给 `analyzeHeadless`，并自行指定已有项目目录及名称：

```text
-process Weixin.dll -noanalysis -readOnly
-scriptPath client_hook/analysis
-postScript ExportSelected.java <反编译输出目录> <ranges.txt路径> 89fc940377a779babbd64c9cd4abe6256663681d92f12802aa2df97a8db18494
```

第三个脚本参数校验 Ghidra 项目的原始文件哈希；不匹配时拒绝导出。
必须使用 `-readOnly` 保留已有分析数据库。

### 操作 0 与操作 1 的调度及回传

| 环节 | 操作 0 | 操作 1 |
| --- | --- | --- |
| 外层包装 | `0x3ba6190`，闭包表 `0x8805de8` | `0x3ba6320`，闭包表 `0x8805f28` |
| 第一层执行槽（表 `+0x10`） | `0x3bf0ce0` | `0x3bf1d10` |
| 调度行为 | 分配 `0x108` 字节执行对象，表 `0x8805e88`，交给 `0x291280` | 分配 `0x100` 字节执行对象，表 `0x8805fc8`，交给同一调度器 |
| 第二层执行槽（表 `+0x10`） | `0x3bf11b0` | `0x3bf21d0` |
| 条件分支 A 的服务 | `0x2c22c00`，输出布尔值及错误文本 | `0x2c24170`，返回值暂未解释 |
| 条件分支 B 的服务 | `0x4c8e2c0`，传入额外的 32 位参数与常量 `1` | `0x4c90170`，返回值暂未解释 |

两层执行对象都保留原数据项的共享引用，不只是朋友圈 ID。
操作 0 的第一层闭包在 `+0x08/+0x10` 保存对象／控制块，在 `+0x18` 保存 32 位参数。
第二层对象仍在上述位置保存这些参数，并在 `+0x20` 构造异步上下文。
操作 1 的第二层对象在 `+0x18` 构造上下文。
服务分支由 `0x3e2b000(数据项)` 的返回值决定；目前没有把该条件正式命名为普通／广告朋友圈。

操作 0 执行后分配 `0x138` 字节的回传任务，入口 `0x3bf1a20`，经 `0x318b90` 调度。
其构造函数 `0x3bf1b90` 把错误文本放在回传任务 `+0x28`，布尔值放在 `+0x48`，
异步上下文放在 `+0x50`。回传入口检查 `+0x48`，失败时使用 `+0x28` 的文本构造异常／错误结果。
这证明存在独立的结果回传路径，**不证明**该布尔值是微信服务器确认。

`0x3bf11b0` 在 `0x3bf1510` 调用 `0x3bf1b90` 时，Ghidra C 输出只显示一个参数。
汇编实际设置 RCX 为输出对象、R8 为上下文、R9 为布尔地址、`[RSP+0x20]` 为错误文本地址；
RDX 在构造函数中未使用。不能据省略参数的 C 输出编写 C ABI 声明。

可复现闭包表扫描：

```powershell
python -B -X utf8 .\client_hook\analysis\analyze_sns.py --artifact <DLL> --table 0x8805de8 --table 0x8805e88 --table 0x8805f28 --table 0x8805fc8 --output .\client_hook\build\sns-closures
```

服务 `0x2c22c00` 进一步构造表为 `0x8611bb8` 的共享对象，调用 `0x4d1fd20` 初始化，
再用 `0x4d22600` 产生数据项用于本地状态处理。初始化对象的表为 `0x89e3df8`，
其中 `+0x08` 的函数 `0x4d206d0` 只复制字符串字段并返回 0，`+0x18` 的函数 `0x4d22510`
只把字符串复制回数据项；它们不是已确认的网络完成回调。
这进一步排除了把相邻 `sns_comment:` 文本或某个虚函数返回 0 直接认定为评论成功的做法。

## 能力边界

当前保留以下限制：

1. 读取只取同账号本地缓存，不主动刷新时间线。
2. 点赞只支持已从同账号联系人数据库核实的好友作者；其他类型不静默套用好友协议。
3. 评论仅支持普通文字；带精确评论引用时明确拒绝，不降级为普通评论。
4. 发布仅支持公开纯文字；不支持图片、视频及自定义可见范围。
5. 直接网络请求可能不更新客户端缓存；不能因旧缓存未变而重发已确认请求。

写操作使用持久请求 ID，绑定账号、操作类型和完整参数；
同 ID 不同参数拒绝，未知状态不能自动重发。不能把文本发送的 `accepted` 或接口调用返回当作朋友圈服务端成功。

HTTP、SDK 和独立的持久幂等队列已接入，使用方式见 [API.md](API.md)。
原生读取实现位于 `api/native_sns.py`，只读取同账号 `db_storage/sns/sns.db` 的缓存；
以 XML 内 ID／作者与数据库列交叉校验，按 uint64 顺序分页。
`NativeBackend` 通过侧车执行写操作，能力状态仅描述构建与原生适配，不代表 MCP 已授权某次执行。
真实缓存读取及取消点赞的隔离 HTTP／SDK 链已验证；点赞、普通评论、公开文字发布分别取得过原生成功结果，
发布结果还校验了返回帖子 ID，重复请求检查保留单次执行。用户反馈风控后停止了真实验证，之后只运行本地回归。
这些有限样本不代表长期运行、所有账号／帖子或风控安全性已验证。

诊断时区分首次提交与随后状态查询。登录态变化可使查询线程以前置校验错误返回，RPC缓冲区仍为零；末次查询的`calls/submitted`不能代表此前没有执行。后端结果`native_observations`有界保留首次与最近查询快照，查询异常另存`query_error`，不据此补发或升级为确认。观察到帖文已出现但客户端随后强退时，仍保留原请求并停止新写入；这类现象不等于已定位到服务器错误码或可用调参消除。

原生探测、提交和查询阶段同时保存到Hook操作库的`meta`键`sns_diagnostics:<request_id>`，只包含阶段时间及原生状态，不复制正文、账号或凭据。提交前诊断存储失败会阻止调用；首次提交结果单独保留，事件列表仅保留最近16条。该记录用于故障定位，不作为重发依据或风控安全证明。

### 取消点赞协议与网络执行器

`0x4cf6760` 调用 `0x4c478f0` 初始化一个 `0x28` 字节的 protobuf 对象，写入：
`+0x08 = 数据项首字段 ID`、`+0x18 = 5`、`+0x20 |= 3`，然后调用 `0x4cf6970`。
这确认了操作 1 分支对应的**协议对象操作值为 5**；它与 UI 分发值 1 是不同层次的枚举。
`0x4c478f0` 是无 unwind 项的叶函数，汇编从入口到 `RET` 为 `0x19` 字节，
设置表 `0x89c6cf8` 并清零 `+0x08..+0x23`。

`0x4cf6970` 将该对象复制到重复对象请求（构造入口 `0x4c479a0`）中，调用公共执行器 `0x4cf7f20`。
后者经 `0x4cfa2c0` 调用 `0x333740`，注册表 `0x89df458` 对应的响应闭包，并等待该请求对象。
输出前两个 32 位字段均为 0 才进入上层成功分支；默认错误含 `-110`，不能把未完成对象当成功。
`0x4cfa2c0` 区分响应闭包标志与请求对象错误路径，并复制错误文本、响应共享引用。
表 `0x89df458` 的执行槽 `0x4cfb1b0` 是跳转到 `0x4cfb300` 的叶 thunk。
后者调用 `0x4cfb6d0` 创建异步执行结果，再经 `0x4cfb520` 等待并取得结果，
将前两个错误字段、文本和响应共享引用复制到输出对象，最后设置 `*(int*)param_1[2] = 1`。
这确认了该标志在结果提取结束后才设置；`0x4cfb520` 还会检查结果类型，不匹配时走异常路径。
实际适配在同一队列／协程执行上下文内调用并清理；不能直接从 Python 远程线程调用这些 C++ 入口。

此外，`0x2c23f10` 的布尔值经 `0x4ce8da0 -> 0x4cefdf0 -> 0x2651f10` 回传，
还会通知本地订阅者；这不是可以独立用作服务端确认的证据。实现使用下述网络包装结果，而不是 UI 包装层布尔值。

### 点赞、评论与发布

普通点赞／评论统一调用 `0x2c17030`，CGI `213`、路由 `/cgi-bin/micromsg-bin/mmsnscomment`。
