WEIXIN 4.1.9.30 · WINDOWS X64 · TEXT PHASE

一条消息，如何从微信
到达你的 agent？

在微信进程内捕获文本记录，经本地服务持久化，再用长轮询交给 agent。发送则沿相反方向进入微信自身的原生业务流程。

本期：私聊与群聊文本HTTP + Python SDK / CLI独立消费者 · 确认后推进无需外部参考仓库

三个边界，一条本地管线

登录、会话与网络通信由官方微信客户端完成。client_hook 在本机适配其消息记录与发送函数，对 agent 暴露稳定的 HTTP 入口。

01 / 微信进程Weixin.exe + 驻留 DLL

MinHook 捕获记录；原生队列执行发送；固定版本校验与生命周期控制。

02 / 本地服务Python + SQLite

管理接收进程、持久事件、消费者进度与发送请求。默认监听 127.0.0.1:30001。

03 / 使用方Agent / SDK / CLI

等待新消息，执行业务，成功后确认；发送时用 request_id 查询同一次操作。

01

监听：先复制，再离开 Hook 做 I/O

  1. 校验目标，安装入口 Hook

    匹配微信版本、核心 DLL 哈希与入口字节，通过 MinHook 安装跳转，保留 trampoline 调用原函数。

  2. 识别入站文本，复制记录

    按固定布局读取 kind、收发端点与正文。当前筛选 kind=1、接收端为本人、发送端非本人；支持全会话或指定会话。

  3. 写入 DLL 内的有界队列

    Hook 只做有界快照与非阻塞入队，不保留原始指针。当前驻留队列为 32 项；争用或满队列计数丢弃，仍调用原函数。

  4. 工作线程输出，Python 跟随读取

    DLL 工作线程把自有副本序列化为 NDJSON，真机文件按 8 MiB 轮转。接收控制进程跟随文件并向 HTTP 服务输出事件。

  5. SQLite 提交后唤醒等待者

    后端规范化为 text 事件，事务写入 SQLite。提交成功后通知条件变量，使正在等待的 GET /messages 返回。

为什么不在 Hook 里直接请求 HTTP？

Hook 正运行在微信调用线程里。磁盘、网络或等待消费者会拖住原调用，因此这些工作放到 DLL 工作线程和 Python 服务中。

UTF-8 严格校验正文 ≤ 64 KiB标识 ≤ 511 字节自有内存快照

文本事件的语义

event_id 是本地事件标识，用于消费去重；它不是微信消息 ID。群消息正文当前保留原始成员前缀，成员候选字段尚不能当作完整验证的发送人。

观察点可能包含记录解析或缓存刷新行为，目前不承诺严格的微信消息去重或完整历史 / 实时区分。

对应源码

runtime_session.inc：驻留采集与会话生命周期
stream_snapshot.c：记录快照
api/backend.py：原生接收适配
api/store.py：事件与消费者持久化

固定版本的原生适配细节

当前入口 RVA 为 0x9DBBF0，过滤原调用返回地址 base + 0x9DACD5 与记录 vtable；0x9DACD0 是内部 CALL 观察位置。记录布局为 0x298 字节，kind 位于 +0xC，两个端点位于 +0x18 / +0x38，正文位于 +0x160。所有地址仅适用于已校验的 4.1.9.30 x64 核心文件。版本变化需重新适配。

02

实时消费：请求挂起，消息到达即返回

Agent 持续发起长轮询：有积压立即取走；没有消息时服务端等待通知。timeout=30 表示最多等待 30 秒，消息在此期间到达就返回，随后发起下一次请求。

一次完整消费

POST /consumers
{"consumer_id":"my-agent","start":"earliest"}

GET /messages?consumer_id=my-agent&timeout=30&limit=100
→ 返回事件批次和 ack_token

执行 agent 业务；按 event_id 去重

POST /consumers/my-agent/ack
{"ack_token":"<本批次 token>"}

继续 GET /messages …

同一消费者未确认的批次会重复返回，进度和 token 保存在数据库中。不同消费者各自推进；同一消费者保持一个等待请求 / 待确认批次。

这里的“未读” = 此消费者尚未确认。
消费不会修改微信界面的已读状态。服务启动前未采集的历史消息，本期无法补取。

至少一次，业务需要去重

业务完成后、ack 前崩溃，重启会再次收到同一事件。因此用 event_id 建唯一键，或让业务操作具备幂等性。示例 agent_listener.py 演示 SQLite inbox 去重；外部副作用仍需自身幂等策略。

有限保留，缺口明确报告

默认保留 7 天 / 1 GiB 逻辑事件数据，可配置。消费者落后超过保留范围返回 410 cursor_expired，需明确 reset。服务未运行、采集丢弃或异常造成的缺口不能由长轮询补回。

交互演示：未确认消息为什么会再出现？

仅在此页面内模拟，不连接微信、不调用接口。先模拟入站，再拉取；观察确认前后的差别。正式服务的数据会保存在 SQLite。

03

发送：先记录意图，再进入微信原生队列

  1. HTTP 校验并持久化请求

    POST /SendTextMsg 检查 toid、UTF-8 正文、长度与 request_id。相同 ID、相同参数返回已保存操作；参数冲突返回 409。入队前保存 queued 状态，待发送队列上限 64。

  2. 工作线程调用驻留 DLL RPC

    请求转为 running。DLL 复制账号、目标、正文到自有 Operation，并保留参数指纹。回调不引用 Python 或临时配置内存。

  3. 提交到客户端自己的执行队列

    校验固定 profile、函数入口、vtable 与所有权约定。准备回调学习实际执行线程，后续执行校验线程身份。

  4. 构造原生文本消息并提交

    取得上下文引用，经工厂创建消息对象，赋值接收者与正文，处理原生字符串的短串 / 堆内存布局。调用已适配的发送提交函数，再按所有权规则清理输出与引用。

  5. 返回本地结果，未完成则查询

    HTTP 最多等待约 2 秒。仍 queued / running 时返回 202，通过原 request_id 查询进展。未知结果保留 unknown，避免自动重发造成重复。

同一条操作，持续查询

POST /SendTextMsg
{"toid":"wxid_xxx",
 "msg":"你好，来自 agent",
 "request_id":"agent-order-001"}

GET /client_hook/requests/agent-order-001

SDK / CLI 封装了接口调用。调用方应保存 request_id；遇到超时先查询原操作。

accepted 是本地接受。
它表示原生发送流程已本地接受请求，delivery_confirmed=false。接口没有对端送达回执。本期真机验收的实际显示由用户另外确认。

对应源码

api/store.py：请求幂等与状态
hook_runtime/sender.py：发送控制
text_send.inc：原生发送与清理

状态含义调用方处理
queued / running等待执行 / 执行中查询同一个 request_id
accepted本地接受，尚无送达回执记录本地结果

unknown崩溃等使提交结果无法确定核查实际会话，避免自动重发
04

启停与验证边界

谁负责关掉监听？

HTTP 服务通过 stdin 管理接收子进程。服务退出导致 EOF，接收侧停止采集；驻留 DLL 也监控控制进程租约。停止时关闭采样、禁用 Hook、等待已进入的回调退出；超时进入 draining，保留仍在使用的会话。

DLL 随微信进程驻留，避免并发卸载。切换旧协议 DLL 需要正常退出并重启微信。目标进程互斥与状态目录锁分别约束接收控制和 SQLite 写入者。

已经验证到哪里？

17 项接口 / 存储 / 原生管线测试及生命周期回归通过。真机已验证短文本私聊与群聊各一次发送、两条入站消息持久消费、入口恢复及重启续取；用户确认两条发送消息均已显示。
