# 会话未读数：微信 4.1.9.30

原生标记会话已读与消息消费确认是两个独立操作。`ack_messages`、消费者 ack 不操作微信未读数。

`POST /client_hook/read/mark` 和 `/client_hook/read/status` 仅接受 `{"event_id":"..."}`，从保留的原事件取得当前账号及会话，不接受任意账号、会话、路径、数据库或函数地址。入站文字才可触发；群事件还须原生结构化 @ 当前账号。MCP另行核验白名单、账号和相同门禁。

原生入口来自 Qt `mmui::ChatSessionCellViewModel` 的 `MarkSessionRead`（metacall id4）：UI 将会话字符串传给 RVA `0x15b3570`，scene=3、flag=1。此包装器不使用第一个参数，完整复制借用的 MSVC string32 到原生自有闭包，经 `0x291280` 投递原生队列；闭包 `0x15d4f50` 取得 SessionManager 后调用 `0x291e990`。不直接写微信数据库，不切换/打开聊天窗口，不添加钩子或动态脚本。

固定核心 SHA256：`89fc940377a779babbd64c9cd4abe6256663681d92f12802aa2df97a8db18494`。`scripts/build_read_sidecar.py` 构建独立常驻模块，锁定模块摘要和入口字节，先执行短/长字符串 ABI 自有进程检查。构建不会加载或调用微信。`hook_runtime/read_rpc.py` 调用时再次校验进程创建时间、当前原生账号、核心、模块及 RPC 入口；模块不卸载。

每个 event_id 先落盘唯一操作，再发起原生调用。进程中断、请求超时或状态未知不自动重试。操作与发送记录分开，7天清理终态记录，进行中延后。原生包装器返回只说明请求已提交，不能当作计数已清零。

状态：`running`、`already_read`（调用前已无未读，未调用原生）、`requested`（原生已提交但未观测到清零）、`confirmed`（只读当前账号 SessionTable，观测计数由正数清零）、`unknown`。只读检查限原事件会话的计数/标识/时间元数据，不读摘要或草稿。`unknown` 后重复 mark 只返回原操作，不重新提交。

语义是清除原生操作实际执行时该会话的未读数，包含此前静默背景；不是按某个服务器消息 ID 逐条已读。执行后新到消息可以形成新未读，不保证聊天角标永久为零。业务只在开始处理合法任务时调用；静默附件或未 @ 群消息不会独立调用。

离线检查不代替真机：真实验收需将本机切到其他会话，再从另一端发送私聊和群真实 @ 指令，不人工打开目标聊天；核对原生计数由正数清零、原生提交一次、回复正常。证据见 `wechat_codex/state/live/read-state-validation.json`，尚无真实样本时不得标为通过。

已取得真机证据：私聊177与群178分别从未读1清零，first_unread_message_id同时清零、last_clear_unread_timestamp前进，每条原生 calls=1、error=0。群正常回复7.385秒并精确关联服务器回显；私聊达到30秒模型时限后中止确认、错误回复accepted并匹配回显。界面角标与群对端收件尚待用户确认，私聊错误收件已由用户贴文确认。
