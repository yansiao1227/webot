## 原生与故障场景

`tests/test_native_api.py` 在新启动的自有 `hook-host.exe` 中加载同一驻留 DLL。接收使用实际 inline Hook 和固定记录布局；发送使用实际 HookSend RPC、客户端式队列和对象所有权 fixture。

发送检查不是读取固定成功值：逐条复读 fixture 捕获的原始 UTF-8 字节，核对 submit 次数、文本和 control 分配/释放、堆及大结果字符串释放计数。覆盖非空内部缓存、错线程拒绝、延迟回调返回 202 后查询同一次操作。所有这些检查均不调用真实微信业务函数。

接收覆盖 60000 字节正文与中转文件轮换；服务不积攒消息列表，正式消息提交至 SQLite 后才对消费者可见。退出登录会停止采样并恢复入口。API 进程崩溃时，接收子进程检测 stdin EOF 并释放采样会话，避免父进程死亡后继续占用 Hook。

存储测试覆盖事务写入失败不产生事件、不推进消费位置，账号隔离、重置使等待请求和旧 token 失效，以及未知发送结果不自动重投。HTTP 测试覆盖 Bearer 鉴权、非法/重复 JSON 字段、别名冲突、未实现路由、并发上限和 SDK 处理失败不确认。

## 真机验收进展

首次只读预检发现旧进程加载了多份历史 Hook DLL，未向该进程追加模块。用户随后明确指定“颜料盒”和“测试群”、允许发送测试文本，并确认已重启微信。新进程 PID 26560 没有历史 Hook 模块，现已通过本期 HTTP 服务加载协议 v3。

真实 `/GetSelfProfile` 与 `/IsLoginStatus` 已取得当前 wxid 和登录状态 3。向“测试群”提交 `CH_HTTP_G_20261022_V3_01 中文消息 😀`，向“颜料盒”提交 `CH_HTTP_P_20261022_V3_01 私聊文本 😀`，各一次。两次首次 HTTP 均返回 202，随后查询同一请求得到 accepted。真实 callback TID 为动态取得的 27872，每项 submit 次数 1、输入已消费、结果已清理、上下文清理成功，正文 UTF-8 长度均为 42 字节；没有因超时重投。用户随后明确确认“两条都已显示”，该人工确认单独记录，不修改原始接口的 `delivery_confirmed=false`，也不将通用接口描述为提供对端送达回执。

用户确认已分别发送入站标记；服务实际捕获私聊和测试群的两条 CH_HTTP_IN，账号与原字段对应，已通过 HTTP 读取并确认。新建第二个消费者取得相同两条事件但不确认，随后停止原生采样：入口和内部 CALL 共 32 字节外部复读与固定字节一致，native state=idle、admitted=0、dropped=0。

重启 API 后复用同一 DLL 基址 `0x64600000`，generation 从 1 变为 2。第二消费者的事件 ID 与 ack token 均保持，确认后读取为空；使用原群聊请求 ID 再调用发送接口返回已保存结果，没有新增 submit。服务现恢复运行。

证据位于本模块 `state/live-validation/`，包含服务输出、发送请求和结果、入站记录、入口恢复、重启续取及人工显示确认。本期短时文本收发验收完成；长期流量和更多真实客户端异常场景仍不属于这次验收的结论。

此前版本的单条群文本采集、旧驻留启停和固定文本一次发送仍属于历史证据。新版已取得的短时私聊/群聊验证不能证明长期运行、全类型接收或历史补取。当前 API 能力状态保守保持 `fixture_verified`，本节单独记录新增真机证据。

真实验收需覆盖私聊、群聊各自双向文本，中文/emoji、消息归属与回显过滤；分别记录本地接受和对端实际收到。未采集到的历史消息、本地原生队列尚未落盘时的崩溃缺口以及业务副作用与确认之间的重复风险，仍按 API.md 中的边界处理。
