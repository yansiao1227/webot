# 微信4.1.9.30：文本记录 Hook 入口和 ABI

2026-10-22。固定目标 SHA256：`89fc940377a779babbd64c9cd4abe6256663681d92f12802aa2df97a8db18494`。所有地址均为 RVA，加运行时模块基址后才是 VA。本轮只读固定 DLL、既有分析文件，编译并执行自有 fixture；未附加微信、执行客户端函数、扫码或提交验证。

## 选择的入口

采用 `Weixin.dll+0x9DBBF0` 的**函数入口、原调用前**作为进程内 detour 位置，且只采集返回地址为 `module+0x9DACD5` 的调用。

`0x9DACD0` 是已有真机采样证据的 CALL 指令，不是普通函数入口。它的前两条是：

```text
9DACC7  mov rcx,[rbp+160h]   ; 已构造0x298记录
9DACCE  mov dl,1
9DACD0  call 9DBBF0
9DACD5  nop                 ; 函数入口时栈顶保存的原返回地址
9DACD6  mov rax,[rbp+160h]   ; 外层构造器自行返回记录，不使用helper的RAX
```

MinHook 改写函数入口并跳转 detour，原 CALL 的返回地址仍在栈上。detour 内直接读取 `_ReturnAddress()`（MSVC）或 `__builtin_return_address(0)`（GCC），不能在另一个普通函数里再取该地址。只对 `return==base+9DACD5 && force==1 && vtable==base+8096DA8` 的记录采样；其余调用直接转交 trampoline。

该门槛恢复的是已验证的记录构造路径，**不是实时入站判据**。历史同步、自己发出的消息或重复转换仍可能经过。业务方向继续结合现场 self_id 和两端点判断。

## 调用约定

静态匹配的 Windows x64 签名：

```c
typedef void (*Wx41930FinalizeFn)(Wx41930Record *record, uint8_t force);
```

| 项目 | 证据及约束 |
|---|---|
| RCX | 借用记录指针；入口保存到RSI |
| DL | 仅低8位参与 TEST DL,DL；0是复用已解析状态，非0强制刷新 |
| 返回 | void；快捷路径不设置稳定RAX，构造器调用后自行重载返回记录 |
| R8/R9、栈参数 | 完整helper函数内未见额外输入读取；不是四参数send接口，也无隐藏返回缓冲区 |
| 寄存器/栈 | 使用Windows x64统一ABI及32字节shadow space，编译器负责非易失寄存器；不用x86 thiscall/stdcall栈约定 |
| force转交 | 将收到的完整字节原样交原函数，不把0x81之类非零值强制变成1 |

名字 Finalize 是分析用名，并未恢复原C++符号。签名是机器级等效接口，不能据此声称源代码声明一定是uint8_t而不是bool/char。这里只在固定构建范围内确认，不覆盖未来版本。

入口前16字节：`56 57 53 48 83 ec 20 48 89 ce 84 d2 75 09 80 be`。前四条指令长度1/1/1/4，恰好7字节，均为push/sub，不包含相对分支或RIP数据。普通5字节入口补丁需要重定位完整7字节；不能拆开最后一条sub。自有ABI fixture使用相同7字节开头并成功运行MinHook trampoline，这不代替对微信实际内存的检查。

直接rel32扫描找到**29处CALL和1处尾跳**，逐一从.pdata边界（叶子thunk为已对齐9E17D0）反汇编，30处均为有效指令。9E17D0先将+118复制到+C，再force=1尾跳到helper；4591F5E用EDX=0调用。可见它是共享的解析/刷新层。间接调用、运行时改写和未被扫描到的路径不在覆盖范围内。

## 原函数的副作用与记录生命期

`9DBBF0(record,force)`：

1. 若force为0且record+270非0，直接返回。
2. 调9DFDB0，根据类型创建/选择record+238/+240的辅助对象及引用计数控制块。
3. +238非空时调用其vtable+10，参数为辅助对象和record。
4. 将record+C起的8字节复制到+118；不是专门的时间戳复制。
5. 必要时创建+248/+250的辅助对象；+180非空时交2210670处理；最后置+270=1。

这不是析构器，也不能用“只读几个字段”概括其行为。虚函数可能继续修改record。采样必须在进入原函数前，之后立刻调用原函数，不主动调用getter/解析器/retain/free。record可能是调用方栈对象，任何指针、std::string头、aux对象引用都不得延迟交给消费者。只传复制后的自有字节快照。

外层9DA310是 `Record*(out,input)` 构造/转换器，返回out；9DBD90在它返回后再用input+70覆盖record+110。因此在本Hook点看到的+110不是外层最终值，也不应先命名为业务时间。不能把helper的void签名套到构造器上。

## 消息记录结构

当前适配的是大小`0x298`、vtable RVA`0x8096DA8`的原生记录，不是protobuf AddMsg的内存布局，也不是出站发送对象。`native/weixin41930.h`为所需字段提供`offsetof`/`sizeof`编译期校验；未知区域保留字节占位，没有伪造完整C++类定义。

| 偏移 | 布局/来源 | 已确认意义及边界 |
|---|---|---|
| +000 | 8字节vtable指针 | 固定类型校验 |
| +00C | uint32，来源input+14，经9DB580赋值 | raw_kind；先只适配已受控验证的kind1文本 |
| +018 | 32字节窄串，input+8嵌套对象的+8 | 端点A；已验证文本中与self对照后可判断来源 |
| +038 | 32字节窄串，input+18嵌套对象的+8 | 端点B；已验证文本中与self对照后可判断目标 |
| +058 | 32字节窄串，由9DB370/9DAEF0派生 | actor候选；不是统一conversation_id |
| +108 | uint64，来自input+50 | 原始数值；没有命名为消息ID |
| +110 | uint64，初值input+48*1000；wrapper随后可覆盖 | 原始数值；本Hook点不是外层最终值 |
| +118 | helper写入record+C的8字节 | 缓存类型/关联状态片段；不当时间戳 |
| +124/+128/+134 | uint32，分别来自input+48/+28/+4C | 原始标量，暂不命名业务字段 |
| +160 | 32字节窄串，input+20嵌套对象的+8 | 正文/载荷；kind1中文UTF-8已有旧真机证据 |
| +180 | 32字节窄串，来自input+38 | 附加来源载荷，当前不采集 |
| +238/+240 | 对象指针/引用计数控制块 | 类型相关解析状态；不跟随、不增减引用 |
| +248/+250 | 对象指针/引用计数控制块 | 来源相关辅助状态；不跟随 |
| +270 | uint8 | 解析/缓存标志；不是incoming标志 |

窄串头为32字节：前16字节为SSO缓冲/堆指针联合体，+10是uint64长度，+18是uint64容量。容量<16用头内字节，否则读取头+0的堆指针。长度以字节计，不是UTF-16字符数。必须校验len<=cap、终止NUL、UTF-8、读成功和前后稳定性；当前复用stream_snapshot的每串511字节及4096字节总预算，超长拒绝，不截断。

输入复制来源的完整默认分支、原protobuf字段名及所有未知对象成员仍未恢复；本适配只覆盖已经有证据的文本采集字段。不要仅因+108是64位就当作消息唯一ID做去重。

## 会话语义

复用既有kind1受控私聊/群文本证据及CLI规则：私聊两端恰有一个等于现场self_id时，另一端为conversation_id。+38=self对应incoming，+18=self对应outgoing；双方相等或不一致保持unknown。合法群ID作为群conversation；只有+58是合法成员wxid且正文以该成员加`:\n`开头时，才标定sender并剥去一次前缀，原文保留。不将其他kind、群出站或无前缀记录强行套用该规则。

当前静态profile不存实际self_id，不读取账号材料；将来真机适配需现场读取并复核已有账号对象链，不能用历史ID代替。
